# Part 1 — Shell Expansion

## Task

Test how Bash handles a variable.

```bash
user="sonu"
echo "$user"
echo '$user'
```

### Expected observation

Double quotes expand the variable.

Single quotes treat `$user` literally.

### Why this matters

Quoting becomes extremely important when scripts handle:

- filenames
- user input
- paths
- commands
- configuration values

# Part 2 — Dynamic Filename

Create:

```bash
dynamic.sh
```

Example structure:

```bash
#!/bin/bash

USER_NAME=$(whoami)
FILE="/tmp/${USER_NAME}_lab.txt"

echo "User: $USER_NAME" > "$FILE"

echo "Created: $FILE"
```

Make it executable:

```bash
chmod +x dynamic.sh
```

Run:

```bash
./dynamic.sh
```

Verify:

```bash
ls -l /tmp/*_lab.txt
```

Then:

```bash
cat /tmp/$(whoami)_lab.txt
```

### Expected result

A file named according to the current username should exist.

The exact filename depends on the user running the script.

---

# Part 3 — Why Dynamic Scripts Are Better

Compare:

```bash
FILE="/tmp/sonu_lab.txt"
```

with:

```bash
FILE="/tmp/$(whoami)_lab.txt"
```

The second is more reusable.

If another user runs the script, the generated filename changes automatically.

### Mentor rule

Whenever you see hard-coded personal/system values, ask:

> "Can this value be detected automatically?"

That question is an important step toward better scripting.

# Part 4 — Trace Script

Create:

```bash
trace.sh
```

It should display useful runtime information.

Example:

```bash
#!/bin/bash

echo "USER=$USER"
echo "HOME=$HOME"

FILE="/tmp/$(whoami)_trace.txt"

echo "FILE=$FILE"

touch "$FILE"

echo "File created:"
ls -l "$FILE"
```

Run:

```bash
chmod +x trace.sh
./trace.sh
```

### Expected output

It should show:

- current username
- home directory
- generated filename
- file metadata

# Part 6 — Cron Service

Check whether cron is running:

```bash
ps -ef | grep cron
```

You may see the cron daemon and the `grep` command itself.

Remember that the `grep` line is created by your search command, so it is not evidence that a second cron service exists.

# Part 7 — Create a Cron Job

Open the user's crontab:

```bash
crontab -e
```

A cron entry follows:

```text
minute hour day-of-month month day-of-week command
```

For a simple test, use a short interval such as:

```text
* * * * * date >> /tmp/cron_test.txt
```

This schedules a command approximately once per minute.

### Important

Cron runs commands in a different execution environment from your interactive shell.

Therefore:

- use absolute paths when practical
- do not assume your interactive working directory
- do not assume every interactive environment variable exists
- redirect output to a known location
- verify the result

---

# Part 8 — Verify Cron

First:

```bash
crontab -l
```

Confirm the entry exists.

Then wait for the scheduled execution.

Check:

```bash
cat /tmp/cron_test.txt
```

You should see date/time output if the job executed successfully.

You can also inspect:

```bash
ls -l /tmp/cron_test.txt
```

# Part 9 — Debugging the Initial Failure

During the lab, attempting:

```bash
cat /tmp/cron_test.txt
```

before the job had created the file produced:

```text
No such file or directory
```

This was useful.

The correct reasoning was:

```text
File missing
   ↓
Check crontab
   ↓
Confirm scheduled command
   ↓
Wait for execution
   ↓
Check file again
```

This is much better than randomly repeating commands.

# Part 10 — Cron Directory Investigation

We also inspected:

```bash
ls /etc/cron.d/
```

This is useful for understanding system-wide scheduled tasks.

Do not confuse:

```bash
crontab -e
```

with:

```text
/etc/cron.d/
```

The first edits the current user's crontab.

The second is part of the system's cron configuration.

# Part 11 — Mistake Analysis

## Mistake A

```bash
cat /etc/cron.d/<entry>
```

The `<entry>` notation was not a real filename.

### Lesson

Documentation placeholders must be replaced with an actual filename.

---

## Mistake B

```bash
cat /etc/cron.d/cron -f -p
```

`cat` does not use the same options as `cron`.

### Lesson

Always check the correct command's documentation:

```bash
man cat
man cron
man crontab
```

# Part 12 — Lab Questions and Answers

### 1. What is variable expansion?

Bash replaces a variable reference such as `$USER` with its stored value.

### 2. What is command substitution?

It allows the output of a command to be inserted into another command.

Example:

```bash
$(whoami)
```

### 3. Why use `${USER_NAME}` instead of `$USER_NAME` sometimes?

Braces clearly mark where the variable name ends, especially when text immediately follows it.

### 4. What does `chmod +x` do?

It adds execute permission so the script can be run directly.

### 5. Why use absolute paths in cron jobs?

Cron may run with a different working directory and environment than an interactive shell.

### 6. What does `crontab -e` do?

It edits the current user's scheduled cron jobs.

### 7. What does `crontab -l` do?

It lists the current user's cron jobs.

### 8. Why did the first `cat /tmp/cron_test.txt` fail?

The scheduled job had not created the file yet.

### 9. Why should output be redirected to a known file?

It provides evidence that the scheduled task executed and gives us something to inspect while debugging.

### 10. Why inspect `/etc/cron.d/`?

It helps understand how system-level scheduled jobs are configured.
