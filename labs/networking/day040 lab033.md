# Lab033 — Linux File Audit Script: Arguments, Options, Loops & Permission Checks

## Lab title
**Lab033: Building and Testing a Multi-Target Linux File Audit Script**

## Purpose
This lab turns the Bash concepts studied in Day 40 into a practical security-oriented utility. The script accepts multiple target paths, validates its input, supports command-line options, checks whether targets exist, identifies their type, checks important permissions, and produces a final audit summary.

The work is directly relevant to defensive security because many real tools begin with the same pattern:

**input → validation → inspection → classification → reporting**

---

## 1. What I built

The script shown in today's work contains these major components:

1. **Initial statistics**
   - current user
   - process ID
   - number of supplied arguments

2. **Argument validation**
   - detects when no target was supplied
   - stops safely instead of running with invalid input

3. **Option handling**
   - `-s` for a summary-style mode
   - `-h` for help
   - `-v` for verbose output
   - invalid options are rejected

4. **Counters**
   - regular files
   - directories
   - missing targets
   - readable targets
   - writable targets
   - executable targets

5. **Audit function**
   - ignores empty arguments
   - checks existence
   - determines whether a target is a regular file, directory, or another type
   - checks `-r`, `-w`, and `-x`

6. **Multiple-target processing**
   - loops through `"$@"`
   - sends every supplied target to the audit function

7. **Final report**
   - prints totals after all targets have been processed

## 3. How I performed the lab

### Step 1 — Create the script

```bash
nano script.sh
```

I created the audit program inside the editor.

### Step 2 — Give it execute permission

```bash
chmod +x script.sh
```

Without the executable bit, attempting:

```bash
./script.sh
```

can produce:

```text
Permission denied
```

This is an important distinction:

- **readable script** does not automatically mean **executable script**
- `chmod +x` adds execute permission

### Step 3 — Run it with targets

Example:

```bash
./script.sh /tmp /etc/passwd /etc/hosts
```

The script receives all three paths through:

```bash
"$@"
```

### Step 4 — Test a missing target

Example:

```bash
./script.sh /does/not/exist
```

This verifies that the script can distinguish a missing target from an existing one.

Examples:

```bash

./script.sh -v /etc/passwd
./script.sh -s /etc/passwd
```

The exact behavior depends on the mode implemented in the script, but the important concept is that command-line options are processed before normal targets.

# 4. Professor questions — answers

## Q1. Why use `$#`?

`$#` stores the number of positional arguments supplied to the script.

Example:

```bash
./script.sh a b c
```

Then:

```bash
$#
```

is:

```text
3
```

### Why it matters
It lets a script detect missing input before performing work.

---

## Q2. What is `$@`?

`$@` represents the positional arguments.

The safest common pattern for processing multiple arguments is:

```bash
for target in "$@"; do
    ...
done
```

Quoting `"$@"` preserves arguments containing spaces as individual arguments.

---

## Q3. What is `$1`?

`$1` is the first positional argument.

Example:

```bash
./script.sh /etc/passwd
```

Then:

```bash
$1
```

contains:

```text
/etc/passwd
```

Other positional parameters include `$2`, `$3`, etc.

---

## Q4. What is `$0`?

`$0` normally contains the script name/path used to invoke the script.

It is useful in help and error messages:

```bash
echo "Usage: $0 [options] target..."
```

This prevents hard-coding the script's name.

---

## Q5. Why use a function such as `audit_target()`?

A function prevents the same checking logic from being copied repeatedly.

Instead of writing the existence/type/permission checks separately for every target, the script can call:

```bash
audit_target "$target"
```

This makes the program:

- shorter
- easier to debug
- easier to extend
- easier to reuse

---

## Q6. What does `-e` test?

```bash
[ -e "$target" ]
```

checks whether the path exists.

It can be used before more specific tests.

---

## Q7. What does `-f` test?

```bash
[ -f "$target" ]
```

checks whether the path is a regular file.

Examples:

- `/etc/passwd` → regular file
- `/tmp` → not a regular file

---

## Q8. What does `-d` test?

```bash
[ -d "$target" ]
```

checks whether the path is a directory.

---

## Q9. What do `-r`, `-w`, and `-x` mean?

```bash
-r
```

Readable

```bash
-w
```

Writable

```bash
-x
```

Executable

Example:

```bash
if [ -r "$target" ]; then
    echo "Readable"
fi
```

These tests are useful for security auditing because unexpected write or execute permissions can be important findings.

---

## Q10. Why quote variables?

Prefer:

```bash
"$target"
```

instead of:

```bash
$target
```

Quoting protects paths containing spaces and prevents unwanted word splitting.

For example, a path such as:

```text
/home/user/My Files/test.txt
```

can break when used incorrectly without quoting.

---

## Q11. Why initialize counters to zero?

Example:

```bash
count_regular=0
count_directory=0
count_missing=0
```

The counters need known starting values before the loop begins.

They can then be incremented:

```bash
count_regular=$((count_regular + 1))
```

---

## Q12. Why use `"$@"` instead of manually checking `$1`, `$2`, `$3`?

Because the number of targets is not fixed.

This:

```bash
for target in "$@"; do
```

allows:

```bash
./script.sh file1 file2 file3 file4 file5
```

without changing the script.

---

## Q13. What is the purpose of a final summary?

The summary converts many individual checks into useful information.

For example:

```text
Regular Files Found: 2
Directories Found: 1
Missing Targets: 1
Total Readable: 3
Total Writable: 1
Total Executable: 1
```

This is much easier to interpret than raw command output.

# 7. Debugging lessons from today's work

When a Bash script fails, use a controlled process.

### Check syntax first

```bash
bash -n script.sh
```

This checks syntax without executing the script.

### Trace execution

```bash
bash -x script.sh /etc/passwd
```

This shows commands as Bash executes them.

### Check permissions

```bash
ls -l script.sh
```

If needed:

```bash
chmod +x script.sh
```

### Check the interpreter

The first line should normally be:

```bash
#!/bin/bash
```

### Test one small piece at a time

Do not immediately debug a 100-line script. Test:

1. argument count
2. option parsing
3. one function
4. one target
5. multiple targets
6. summary counters

# 8. Important mistakes to avoid

### Mistake 1 — Forgetting executable permission

```bash
./script.sh
```

may fail with:

```text
Permission denied
```

Fix:

```bash
chmod +x script.sh
```

### Mistake 2 — Missing spaces inside `[ ]`

Correct:

```bash
[ -e "$target" ]
```

Not:

```bash
[-e "$target"]
```

### Mistake 3 — Unquoted paths

Use:

```bash
"$target"
```

### Mistake 4 — Incorrect loop termination

For a `for` loop:

```bash
for target in "$@"; do
    ...
done
```

The `done` must match the loop.

### Mistake 5 — Mixing option arguments and target arguments

Option parsing should be completed before processing normal targets.
