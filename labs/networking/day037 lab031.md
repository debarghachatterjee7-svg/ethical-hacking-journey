# Day 037 — Lab 031: Bash File Audit & Automation

## Title
**Bash File Audit & Multi-Target Inspection Lab**

## Description
Today's practical lab combined previously learned Bash concepts with the new ideas of **`for` loops, multi-argument processing, counters, and arithmetic**.

The goal was to build a small Linux file-audit script that can accept multiple paths, check whether they exist, identify their type, inspect permissions, and keep a count of the targets checked.

This lab is designed as a bridge between learning individual Bash commands and using Bash to build useful security-oriented automation.

---

## Lab Objective

Build a Bash script that can:

1. Display the current user.
2. Display the script process PID.
3. Display the number of supplied arguments.
4. Detect when no argument was supplied.
5. Process multiple paths using `"$@"`.
6. Check whether each path exists.
7. Identify regular files and directories.
8. Check read/write/execute permissions.
9. Maintain a counter.
10. Use Bash arithmetic.
11. Use `&&` and `||` for compact success/failure handling.

# 3. Processing Multiple Targets

The script used:

```bash
for target in "$@"
do
    ...
done
```

This is important.

If the command is:

```bash
./audit.sh /etc/passwd /etc/hosts /tmp
```

then `"$@"` supplies all the arguments, and the loop processes them one at a time.

Conceptually:

```text
"$@"
  |
  +--> /etc/passwd
  |
  +--> /etc/hosts
  |
  +--> /tmp
```

The loop then examines each target.

# 4. Checking Whether a Path Exists

The script used:

```bash
if [ -e "$target" ]; then
```

The `-e` test checks whether the path exists.

This is different from:

```bash
-f
```

which specifically checks for a regular file.

And:

```bash
-d
```

which checks for a directory.

# 5. Counting Targets

The script initialized:

```bash
count=0
```

and then used:

```bash
count=$((count + 1))
```

This is Bash arithmetic.

The idea is:

```text
Start: 0
Target 1 → 1
Target 2 → 2
Target 3 → 3
```

At the end, the script can report how many paths it processed.

# 6. File Type Detection

The script used:

```bash
if [ -f "$target" ]; then
    echo "Type: Regular file"
```

This allows the script to distinguish ordinary files from other filesystem objects.

A more complete implementation can add:

```bash
elif [ -d "$target" ]; then
    echo "Type: Directory"
else
    echo "Type: Other"
fi
```

# 7. Permission Checks

The script used:

```bash
[ -r "$target" ] && echo "Readable: Yes" || echo "Readable: No"
[ -w "$target" ] && echo "Writable: Yes" || echo "Writable: No"
[ -x "$target" ] && echo "Executable: Yes" || echo "Executable: No"
```

### Meaning

| Test | Meaning |
|---|---|
| `-r` | Path is readable |
| `-w` | Path is writable |
| `-x` | Path is executable/searchable according to filesystem semantics |

This is directly relevant to Linux permissions and security auditing.

# 8. Important Practical Issue I Encountered

I created/edited:

```bash
day037.sh
```

but then attempted to execute:

```bash
./audit.sh /etc/passwd /etc /this/does/not/exist
```

The shell returned:

```text
-bash: ./audit.sh: Permission denied
```

I then ran:

```bash
chmod +x day037.sh
```

but tried to execute `audit.sh` again.

## Why this happened

The permission was changed on:

```text
day037.sh
```

but the command attempted to run:

```text
audit.sh
```

These are different files.

So:

```bash
chmod +x day037.sh
```

does **not** make:

```bash
./audit.sh
```

executable.

### Correct approach

If the actual script is `day037.sh`:

```bash
chmod +x day037.sh
./day037.sh /etc/passwd /etc /this/does/not/exist
```

Or, if the intended script name is `audit.sh`:

```bash
chmod +x audit.sh
./audit.sh /etc/passwd /etc /this/does/not/exist
```

### What this taught me

This was actually a useful debugging lesson:

> **Always verify the exact filename before changing permissions or executing a script.**

Useful commands:

```bash
ls -l day037.sh
ls -l audit.sh
```

The permission bits make it possible to see whether the file has execute permission.

# 9. Lab Questions & Answers

## Q1. Why is `$@` better than `$1` when processing multiple inputs?

`$1` contains only the first argument.

`$@` represents all supplied positional arguments.

For example:

```bash
./audit.sh file1 file2 file3
```

Then:

```text
$1 → file1
$2 → file2
$3 → file3
$@ → file1 file2 file3
```

Therefore, `"$@"` is better when the script should process an unknown number of inputs.

---

## Q2. Why do we quote `"$file"` or `"$target"`?

Quoting protects arguments that contain spaces or special characters.

For example:

```text
my report.txt
```

Without quotes, Bash may interpret this as two separate words.

Using:

```bash
"$target"
```

keeps the entire path together.

This is a very important Bash habit.

---

## Q3. What happens if the user provides no arguments?

`$#` becomes `0`.

The script detects this:

```bash
if [ "$#" -eq 0 ]; then
```

and can print an error and stop:

```bash
exit 1
```

This prevents the rest of the script from operating on an empty input.

---

## Q4. Why is `-e` different from `-f`?

`-e` asks:

> Does this path exist?

`-f` asks:

> Is this path a regular file?

Therefore a directory can satisfy `-e` but fail `-f`.

Example:

```bash
[ -e /tmp ]
```

can be true because `/tmp` exists.

But:

```bash
[ -f /tmp ]
```

is false because `/tmp` is a directory.

---

## Q5. Why can a directory be readable but not writable?

Linux permissions treat directory operations differently from ordinary file contents.

For a directory:

- `r` allows listing directory entries.
- `w` allows modifying directory entries, subject to other permissions.
- `x` allows accessing/searching entries within the directory.

So directory permissions should not be interpreted exactly like regular-file permissions.

---

## Q6. Why is the counter initialized before the loop?

The counter needs a known starting value.

```bash
count=0
```

means:

> Nothing has been processed yet.

Each iteration then increments it.

---

## Q7. Why use `count=$((count + 1))`?

Because Bash arithmetic is performed inside:

```bash
$(( ... ))
```

The command means:

```text
old count + 1
```

and stores the new value back in `count`.

---

## Q8. What happens if a `while` loop's condition never becomes false?

The loop can continue indefinitely.

This is called an **infinite loop**.

For example:

```bash
count=1

while [ "$count" -le 5 ]
do
    echo "$count"
done
```

The condition never changes because `count` is never increased.

A proper loop needs an update such as:

```bash
count=$((count + 1))
```

# 12. Key Debugging Lesson

The most important practical mistake today was not a Bash syntax problem.

It was a **filename mismatch**:

```text
Created/edited → day037.sh
chmod applied → day037.sh
Executed → audit.sh
```

This reinforces a broader security/engineering habit:

> Read the command, verify the target, then execute.

Useful checks:

```bash
pwd
ls -l
ls -l day037.sh
ls -l audit.sh
```

Don't blindly retry a command after an error. First understand what the error is telling you.
