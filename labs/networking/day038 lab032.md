# LAB032 --- Bash Functions, File Auditing & Debugging

## Lab Title

**Bash Functions, Multi-Target File Auditing and Systematic Debugging**

## Objective

Today's lab focused on turning previously learned Bash commands into
reusable program logic. The main goals were:

-   Create and call Bash functions.
-   Pass arguments into functions.
-   Use `local` variables.
-   Process multiple command-line arguments with `"$@"`.
-   Test paths with `-e`, `-f`, and `-d`.
-   Test permissions with `-r`, `-w`, and `-x`.
-   Use counters and arithmetic expansion.
-   Build a small file/permission auditing tool.
-   Detect and fix Bash syntax errors.
-   Use `bash -n` and `bash -x` as debugging tools.
-   Understand how a script can turn raw Linux information into a useful
    report.

## 1. Lab 1 --- Bash Function Basics

### Script

`function_test.sh`

The script contained a simple function:

``` bash
greet() {
    echo "Hello, $1"
}

greet "Linux"
greet "Security"
greet "Bash"
```

### First problem encountered

The script was initially executed before it had execute permission:

``` text
-bash: ./function_test.sh: Permission denied
```

The problem was fixed with:

``` bash
chmod +x function_test.sh
```

The script then executed successfully:

``` text
Hello, Linux
Hello, Security
Hello, Bash
```

### What this demonstrated

The failure was not a problem with the function itself. It was a
**file-permission issue**.

This reinforced the relationship between:

``` text
script file
    ↓
execute permission
    ↓
shell execution
```

It also showed why checking permissions is important when debugging a
script.

## 2. Lab 2 --- Multi-Target File Checking

### Script

`filetest.sh`

The script accepted several paths:

``` bash
./filetest.sh /etc/passwd /tmp /does/not/exist
```

It classified each target.

Example output:

``` text
[+] Regular file: /etc/passwd
[+] Directory: /tmp
[-] Does not exist: /does/not/exist
```

### Concepts used

-   `$1`, `$2`, etc. --- positional arguments
-   `"$@"` --- all supplied arguments
-   `for` loop --- process each target
-   `-e` --- path exists
-   `-f` --- regular file
-   `-d` --- directory
-   `if / elif / else` --- decision making
-   `return` --- communicate function success/failure

### Why `"$@"` matters

Instead of writing separate code for every possible target, the script
can accept any number of paths:

``` bash
for target in "$@"; do
    ...
done
```

This makes the script scalable.

## 3. Lab 3 --- Permission Audit

### Script

`permission_audit.sh`

The script inspected:

``` text
/etc/passwd
/tmp
/does/not/exist
```

For each target it checked:

-   existence
-   regular-file status
-   directory status
-   readability
-   writability
-   executability

The relevant tests were:

``` bash
[ -e "$target" ]
[ -f "$target" ]
[ -d "$target" ]
[ -r "$target" ]
[ -w "$target" ]
[ -x "$target" ]
```

### Example result

For `/etc/passwd`:

``` text
[+] Exists
[+] Regular File
[✓] Readable
[✗] NOT Writable
[✗] NOT Executable
```

For `/tmp`:

``` text
[+] Exists
[+] Directory
[✓] Readable
[✓] Writable
[✓] Executable
```

### Why this is useful

This is the beginning of defensive automation.

A security-oriented script can use the same idea to inspect:

-   sensitive files
-   configuration files
-   directories
-   scripts
-   permission mistakes
-   potentially dangerous write/execute permissions

The lab did not perform any intrusive activity; it was local permission
auditing.

# 4. Lab 4 --- Counter and Summary

### Script

`lab4.sh`

The script accepted multiple paths and maintained:

``` bash
existing_count=0
missing_count=0
```

For every argument:

``` text
if target exists
    increment existing_count
else
    increment missing_count
```

Arithmetic expansion was used:

``` bash
existing_count=$((existing_count + 1))
missing_count=$((missing_count + 1))
```

The final report looked like:

``` text
===== Audit Summary =====
Targets checked: 5
Existing: 4
Missing: 1
=========================
```

### What was learned

The script now does more than print information.

It:

1.  accepts input
2.  processes input
3.  makes decisions
4.  maintains state
5.  calculates results
6.  produces a summary

That is the basic structure of a real automation tool.

# 5. Debugging Problems Encountered

This was one of the most useful parts of today's lab.

## Problem A --- Execute permission

Error:

``` text
Permission denied
```

Fix:

``` bash
chmod +x script.sh
```

Lesson:

> When a script refuses to execute, check its permissions before
> changing the code.

------------------------------------------------------------------------

## Problem B --- Syntax error in `lab4.sh`

The first version produced an error similar to:

``` text
syntax error near unexpected token `else'
```

and later:

``` text
syntax error near unexpected token `done'
```

This indicated that Bash's control-flow structure was broken.

The important structure is:

``` bash
for ...
do

    if ...
    then
        ...
    else
        ...
    fi

done
```

The corrected script restored the missing/misplaced control-flow
structure.

------------------------------------------------------------------------

## Problem C --- Using the debugger

The script was tested with:

``` bash
bash -x lab4.sh
```

This exposed the point where Bash stopped parsing/executing correctly.

### Debugging workflow learned

``` text
Problem
  ↓
Read the error
  ↓
Check syntax
  ↓
bash -n script.sh
  ↓
If syntax is valid, use bash -x
  ↓
Inspect variables and control flow
  ↓
Fix
  ↓
Run again
```

# Professor Questions --- Answers

## 1. What is a Bash function?

A Bash function is a named reusable block of commands. It allows the
same logic to be called multiple times without rewriting it.

------------------------------------------------------------------------

## 2. Why are functions better than repeating commands?

They reduce duplication, make scripts easier to read, simplify
debugging, and allow one piece of logic to be reused for many inputs.

------------------------------------------------------------------------

## 3. What does `$1` mean inside a function?

Inside a function, `$1` refers to the first argument passed to that
function.

Example:

``` bash
greet "Linux"
```

Inside `greet`, `$1` becomes `Linux`.

------------------------------------------------------------------------

## 4. Why use `local`?

`local` keeps a variable limited to the current function. This reduces
accidental changes to variables outside the function.

Example:

``` bash
check_file() {
    local target="$1"
}
```

------------------------------------------------------------------------

## 5. What does `return 0` mean?

It normally indicates successful execution.

``` bash
return 0
```

------------------------------------------------------------------------

## 6. What does `return 1` mean?

It represents a failure/non-success status.

``` bash
return 1
```

The exact non-zero value can vary, but zero conventionally means
success.

------------------------------------------------------------------------

## 7. Function `$1` vs script `$1`

They depend on the current execution context.

At script level:

``` bash
./script.sh file.txt
```

`$1` is `file.txt`.

Inside:

``` bash
check_file "$1"
```

the function receives that value as its own `$1`.

------------------------------------------------------------------------

## 8. Why is `"$@"` useful?

It represents all positional arguments individually.

This makes:

``` bash
for target in "$@"
```

ideal for processing an arbitrary number of targets.

------------------------------------------------------------------------

## 9. What does `bash -n` do?

It checks a script for syntax problems without executing the commands.

``` bash
bash -n script.sh
```

------------------------------------------------------------------------

## 10. What does `bash -x` do?

It traces commands as Bash executes them.

``` bash
bash -x script.sh
```

This is useful when the script runs but behaves unexpectedly.

------------------------------------------------------------------------

## 11. What does `$?` represent?

It contains the exit status of the most recently executed command.

Convention:

``` text
0       = success
non-zero = failure
```

------------------------------------------------------------------------

## 12. Why are file tests useful?

They let a script make decisions based on the state of the filesystem.

For example:

``` bash
[ -f "$target" ]
```

can determine whether a target is a regular file.

------------------------------------------------------------------------

## 13. Why is a counter useful?

Counters allow a script to summarize results.

Instead of producing hundreds of individual lines, the program can
report:

``` text
Checked: 100
Existing: 94
Missing: 6
```

------------------------------------------------------------------------

## 14. Why validate input?

Without validation, a script may operate on invalid paths or unexpected
input and produce misleading results or errors.

Validation makes automation safer and more predictable.

------------------------------------------------------------------------

## 15. How could this become a security-audit script?

The same architecture could later be extended:

``` text
Input
 ↓
Validate target
 ↓
Inspect file
 ↓
Inspect permissions
 ↓
Inspect ownership
 ↓
Inspect configuration
 ↓
Collect findings
 ↓
Generate report
```

That is a realistic foundation for your future Bash security-audit
project.
