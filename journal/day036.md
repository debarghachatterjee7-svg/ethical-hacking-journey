# 2. Concepts Learned Today

## 2.1 Environment Variables

I revised and used variables such as:

```bash
echo "$USER"
echo "$HOME"
echo "$PATH"
echo "$SHELL"
echo "$PWD"
```

### What are they?

Environment variables are pieces of information supplied to processes by the shell/environment.

For example:

```bash
$USER
```

represents the current username.

```bash
$HOME
```

represents the user's home directory.

```bash
$PATH
```

contains directories where the shell searches for executable commands.

### Why this matters

Hard-coding:

```text
/home/sonu
```

makes a script specific to one account.

Using:

```bash
"$HOME"
```

makes it adaptable.

This is an important scripting habit.

# 3. Command Substitution

I learned/revised:

```bash
$(command)
```

Example:

```bash
echo "User: $(whoami)"
```

The shell runs:

```bash
whoami
```

and places its output into the surrounding command.

Another practical example:

```bash
FILE="/tmp/$(whoami)_lab.txt"
```

This creates a dynamic filename.

### Mental model

Think:

```text
$(command)
```

as:

> "Run this command here and insert what it returns."

---

# 4. Dynamic File Creation

I used command substitution to create a file whose name depends on the current user.

Example:

```bash
FILE="/tmp/$(whoami)_lab.txt"
echo "User: $(whoami)" > "$FILE"
```

This is more powerful than manually writing one fixed filename.

### Real-life uses

Dynamic paths are useful for:

- per-user logs;
- temporary files;
- backup names;
- system scripts;
- automated reports;
- testing;
- security tools.

# 5. Bash Script Execution

I worked with scripts such as:

```text
dynamic.sh
trace.sh
audit.sh
```

A Bash script normally starts with:

```bash
#!/bin/bash
```

This tells the system which interpreter should execute the script.

I also practiced:

```bash
chmod +x script.sh
```

followed by:

```bash
./script.sh
```

### Important distinction

Writing a script does not automatically make it executable.

`chmod +x` gives the execute permission required to run it directly as:

```bash
./script.sh
```

# 6. Cron

Cron was one of the most important concepts today.

Cron is used to execute commands automatically according to a schedule.

For example, a job can be scheduled to run:

- every minute;
- every hour;
- every day;
- on a particular day;
- at a particular combination of time/date conditions.

### Basic structure

```text
minute hour day-of-month month day-of-week command
```

Example:

```text
* * * * * /path/to/script.sh
```

means the command is scheduled every minute.

---

# 7. Crontab

Important commands:

```bash
crontab -l
```

Lists the current user's cron jobs.

```bash
crontab -e
```

Edits the current user's cron jobs.

I used:

```bash
crontab -e
```

and created a test schedule that produced:

```text
/tmp/cron_test.txt
```

I then verified the result with:

```bash
cat /tmp/cron_test.txt
```

The timestamp demonstrated that the scheduled command had executed.

---

# 8. `/etc/cron.d/`

I also inspected:

```bash
ls /etc/cron.d/
```

This directory contains system-level cron configuration entries.

This is different from the user's personal crontab.

### Security importance

When analyzing an authorized Linux system, scheduled jobs can reveal:

- maintenance tasks;
- automated scripts;
- backup processes;
- periodic system actions;
- security monitoring;
- unexpected scheduled activity.

This makes cron an important concept for both administration and security analysis.

# 9. Verifying Cron With Process Information

I used:

```bash
ps -ef | grep cron
```

to find the cron process.

This connected today's cron lesson with earlier process-management learning.

### Why this is useful

If a scheduled job does not work, one possible question is:

> "Is the scheduling service actually running?"

Process inspection helps answer that.

# 10. Debugging Lessons

I encountered several small mistakes today.

## Mistake 1 — File did not exist

```bash
cat /tmp/cron_test.txt
```

returned:

```text
No such file or directory
```

Later the file appeared after the scheduled job executed.

### Lesson

Automation may be correct but simply has not executed yet.

---

## Mistake 2 — Literal placeholder syntax

I tried something similar to:

```bash
cat /etc/cron.d/<entry>
```

The shell treated `<` and `>` as special syntax.

### Lesson

Documentation placeholders must be replaced with actual values.

---

## Mistake 3 — Wrong command options

I attempted to pass options intended for `cron` to `cat`.

### Lesson

Always ask:

> "Which command is receiving this option?"

The shell syntax may be valid-looking but still logically wrong.

## Redirection

```bash
>
>>
2>
2>/dev/null
```

### Important

```bash
>
```

redirects standard output and normally replaces the target.

```bash
>>
```

appends output.

```bash
2>
```

redirects standard error.

```bash
2>/dev/null
```

discards standard error.

---

## Pipes

```bash
|
```

connects one command's output to another command's input.

Example:

```bash
ps -ef | grep cron
```

---

## Archives and Compression

### gzip

```bash
gzip file.txt
```

compresses a file.

### gunzip

```bash
gunzip file.txt.gz
```

decompresses a gzip file.

### tar

```bash
tar -cvf backup.tar folder
```

creates an archive.

```bash
tar -xvf backup.tar
```

extracts it.

### gzip + tar

```bash
tar -czvf backup.tar.gz folder
```

creates a gzip-compressed tar archive.

```bash
tar -xzvf backup.tar.gz
```

extracts it.

### Important distinction

`tar` is primarily an archiving tool.

`gzip` is a compression tool.

They are commonly combined:

```text
tar → archive
gzip → compress
```

## Networking Basics Already Learned

Important commands/concepts include:

```bash
ip addr
ip link
ip route
ss -tuln
ping
```

### `ip addr`

Shows network interfaces and assigned addresses.

### `ip link`

Shows network interfaces and their link state/MAC information.

### `ip route`

Shows routing information, including the default route.

### `ss -tuln`

Helps inspect listening TCP/UDP sockets.

### `ping`

Uses ICMP echo requests to test reachability and observe latency.

Important distinction:

> A successful ping means the target responded to ICMP. It does not prove that every service or port on that host is reachable.
